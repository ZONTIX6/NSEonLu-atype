# 跃鹿框架边界整理

用户已批准按“反向依赖 → 电机策略 → 底盘职责”顺序整理，保持现有功能和控制逻辑不变。基线为 `53b9c51`，直接复用当前干净工作区。

## 设计

1. 整车 USB 数据采集和 Flash 轮询属于应用调度，移至 `application/runtime/robot_telemetry.c`。`modules/telemetry` 保留格式、协议、流传输与调参引擎。采集顺序、时钟读取位置、20 ms 调度和 USB 输出保持原样。标定协议接收应用复制的 `FcLimits`，不包含板级应用头；USB 会话初始化不清除车型配置。
2. DJI 驱动保留反馈、PID、停止证明、最终安全门控、量化与唯一 CAN 提交路径。四轮 PID 参数注册/恢复、自动整定接管/恢复和台架策略移到 DJI 调参适配器，由输出组注册的策略回调接入。回调分别位于原来的注册、周期开始、参考值处理、输出限制后、全车禁止输出及提交记录位置，不增加任务。
3. 速度底盘应用拆为周期控制、初始化和调参实现。应用私有状态只在本目录共享；消息话题及公开 `ChassisInit/ChassisTask`、速度/遥测快照接口保持不变。功率算法和小陀螺算法仍由现有模块实现。

## 不变量

- 所有控制参数、单位、车型宏、CAN ID/分组、硬件连接和协议字节保持不变。
- 初始化顺序、任务周期/优先级/栈、采样与门控顺序、临界区以及 Flash schema 保持不变。
- 不更改单例策略，不把快环改为消息队列，不修改力控、预测功控、KF 或小陀螺算法。
- 不推送、不烧录；完成软件验证后提交本次相关改动。

## 验证

先运行基线回归。扩展架构检查覆盖遥测和电机适配目录，并用人工构造的反向依赖与驱动策略依赖验证检查器。协议测试覆盖应用注入限制、会话重置及原字节结果。电机回归覆盖四轮和其余五电机隔离、整定退出恢复、晚到停机、CAN 失败及既有黄金夹具。底盘拆分采用原函数/常量机械迁移，比较迁移前后函数内容，并构建默认、自适应、正弦、双板、力控和标定配置。最终运行完整主机回归、Make/CMake 矩阵及产物检查，更新相关文档索引。静态/主机验证不宣称实测硬件耗时相同。
