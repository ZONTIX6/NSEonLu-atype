# 卡尔曼底盘移植方案（讨论稿）

日期：2026-11-11

目标工程：`D:/nsezxb/NSEonLu - atype`，分析基线 `7642f756`

参考工程：`D:/nsezxb/gimbal-fed infantry  A - Kalman/gimbal-fed infantry  A - Kalman/gimbal-fed infantry`，分析基线 `236fb95`，代码标记 frame 19。

## 1. 我的建议

分两阶段：先把参考工程的**整车速度估计和候选补偿作为影子运行**，记录与现有底盘速度、轮速目标的差异；验证硬件、坐标、时间、参数和实际工况后，再单独评审是否开放限幅后的速度补偿。第一阶段不改变电机参考、PID、功控、自旋、急停和既有遥测含义。这个文档只提出方案，不代表已经实现或通过实车验收。

参考工程的 KF 是四状态 `[vx, ax, vy, ay]`，在启动后的固定导航系融合轮速反解的平移速度与 IMU 去重力加速度；补偿在命令参考系形成。它不只是一个滤波器：还包括观测冲突、恢复、补偿许可、渐入、限幅及诊断。参考工程默认 `MC_SHADOW`，**不能据此认为主动补偿已在目标车验证有效，也不能称为防滑控制**。

## 2. 可以选择的方案

| 方案 | 内容 | 优点 | 主要代价 |
| --- | --- | --- | --- |
| A（推荐） | 移植源运动估计和保护，先影子，后经验收再考虑速度补偿 | 可直接比较现有行为；故障时原控制链仍可运行；保留参考算法的核心价值 | 需适配 INS、时钟、坐标和诊断，主动补偿不能马上使用 |
| B | 只输出融合速度，不计算或接入补偿 | 接入面较小，适合先验证传感器 | 无法验证源控制器的候选补偿；后续仍需二次集成 |
| C | 直接替换当前底盘控制为参考工程整套控制 | 与参考实现更接近 | 会改变轮速分配、功控、跟随及安全链，车体参数和软件兼容性未验证，风险和排查成本高 |

建议选择 A；如果当前主要目标仅是观测实际车速，可先实施 A 的估计部分，相当于 B。力控分支与多轮型扩展不属于首批范围。

## 3. 两个工程的实际差异

| 项目 | 参考工程 | 目标工程及影响 |
| --- | --- | --- |
| 设备 | STM32F427 A 板、MPU6500；默认 X 全向轮 | 同为 A 板和 MPU6500，四轮 CAN1 ID 为 LF/RF/LB/RB = 1/4/2/3；**接口相似不等于实车安装一致** |
| 电机及控制 | `modules/chassis_motion/` 输出候选速度补偿 | 默认 `CHASSIS_CONTROL_MODE=0` 速度控制；`application/chassis/chassis.c` 做模式/运动学、功率预算和轮速下发；`CHASSIS_CONTROL_MODE=1` 是独立力控 |
| 现有速度 | 融合轮速和 IMU | `modules/algorithm/chassis_velocity.[ch]` 是四轮里程计，输出前/右 m/s、车体旋转 rpm；保留其现有含义作为对照 |
| 另一个 KF | 整车四状态融合 | `docs/chassis-speed-observation.md` 是默认关闭的**单轮**两状态 KF 影子实验，单位为转子 rad/s；两者不能混为同一开关或参数 |
| INS | 输入要求同源时间、姿态、去重力加速度，随云台运动时还需三维杆臂和相对位姿 | `modules/imu/ins_service.c` 内部计算 `MotionAccel_b/n`，但 `INSSnapshot_s` 仅公开姿态、含重力 `Accel`、毫秒时间和有效性；不能把原始 `Accel` 当作运动加速度 |
| 时间 | IMU 和轮反馈各自带序号与本机微秒时间 | 四轮反馈已有 `rx_sequence/rx_tick_ms`，另有接收周期计数；INS 快照缺少同一微秒时基的序号和运动加速度。CAN 接收时刻也不是电调真实采样时刻 |
| 参数 | 源 `config/config.c` 当前源码默认轮半径 76 mm，且有特定车辆的杆臂及 13.5 ms 相位提前量 | 目标 `application/robot_def.h` 默认轴距 350 mm、轮距 300 mm、轮半径 60 mm、减速比 19；均应核对构建覆盖与实物。源移植文档还保留过 72.5 mm 的历史说明，存在与当前源码不一致，不应作为目标参数 |
| 头文件 | 源 `modules/chassis_motion/chassis_motion.h` 使用 `CHASSIS_MOTION_H` | 目标已有 `application/chassis/chassis_motion.h`，文件名和 include guard 均冲突；必须给移植模块改为独立名称及 guard，并检查所有 include，不能靠 include 顺序碰运气 |

目标 README 说明当前固件仍缺烧录、架空和实车验收。源工程已有影子实验，但这也不能替代目标车的验收。

## 4. 推荐架构和数据流

```text
四轮真实接收反馈 ─┐
INS 同采样快照 ───┼─> 目标车适配：时间 / 单位 / 坐标 / 杆臂
云台相对角与状态 ─┘                 │
                                   ▼
                  源 KF + 观测冲突和控制许可（影子）
                                   │
                  融合速度 / 质量状态 / 候选补偿 / 拒绝原因
                                   │
                              只读诊断记录

原命令 → 原跟随和自旋 → 原运动学 → 原功控 / 安全 / PID → 电机
```

1. 首批只支持目标的 `CHASSIS_CONTROL_MODE=0`，优先单板、现有 X 全向轮。编译开关默认关闭；力控构建保持原行为，开启不支持的组合应明确拒绝，不能静默接管。
2. 将源 `modules/chassis_motion/{kinematics,chassis_motion,motion_port}` 中需要的通用部分按独立目录和唯一头文件名引入；对照两边 `kalman_filter.[ch]` 及 CMSIS DSP 的接口、矩阵行为和内存管理后决定复用或隔离，禁止直接覆盖目标公共滤波器或姿态 EKF。
3. 在目标 `application/chassis/` 增加只读适配层：从真实更新的四轮反馈及 INS 快照组装输入，复用现有模式和速度反馈，单一任务每周期运行一次估计。保持当前 `ChassisGetVelocitySnapshot()` 的数据来源与单位不变，新估计使用独立快照及独立有效位。
4. `B` 统一前/左/上，轮序 LF/RF/LB/RB；目标当前车体系横向正方向是右，适配层只做一次有测试的符号转换。明确云台相对角定义、角度连续性及转子 deg/s 与 rpm 的换算。目标现有 `wz` 指令量不能直接视为物理 rad/s，必须从现有运动学和实测标定建立对应关系。
5. 扩展 INS 的一致性发布，至少包含四元数或可核验的导航系航向、去重力加速度、陀螺、实际样本序号/本机接收时间和有效状态。若 IMU 跟随云台 pitch/yaw，需按目标车安装轴、相对姿态和杆臂在采样层完成三维中心加速度校正；数据缺失时标记无效，禁止主动补偿。须核对源姿态恢复及观测保护所需信息，缺失的状态不可用常量冒充。
6. 所有年龄、轮间偏差和 dt 用可证明属于同一本机单调时基的真实事件时间计算；周期计数换算要处理回绕、复位和 tick/cycle 原子一致性。缺少真实样本时间时记录为接收时间及其不确定度，不伪造采样序号或精度；不满足对齐条件时保持影子且标明不可用。
7. 第一阶段诊断单独输出：轮速估计与 KF 的平移速度、创新/残差、有效状态、退出和控制禁止原因、候选补偿、时间年龄/偏斜、模式、轮在线、丢样计数及功控限制状态。优先利用现有只读采集设施，版本化扩展，避免破坏已有 USB/VOFA 数据协议。

## 5. 后续主动补偿的接入边界

只有影子数据和实车证据达到验收要求，且另行确认后，才考虑在**现有速度模式**中把有界平移补偿加入原命令/运动学输入，随后仍经过目标工程原有轮速约束、功率分配、急停、驱动在线、热保护和 CAN 输出。具体插入点要先用单位测试证明与 `ChassisResolveMotion()` 的坐标转换只执行一次，并验证自旋功率策略看到的目标与实际执行目标一致；不得把源轮速结果直接写入电机、覆盖功控输出或引入第二条执行通路。

补偿必须满足源算法独立许可：估计有效只是必要条件；观测一致窗口、稳定时间、误差界限、执行器状态及渐入条件都要满足。估计失效、IMU 超时、时间异常、观测冲突、模式切换或许可丢失时立即撤销补偿并清理历史；重新满足完整恢复条件后才能渐入。命令超时、急停和驱动故障仍按目标原有安全链停驱，**KF 失效只意味着补偿不可用，不自动代表电机已停止**。不能将异常时回退基线解释为绕过目标现有故障停驱。

初始固定增益、补偿上限、变化率、恢复窗口、噪声方差和观测阈值需要目标车数据与测试依据；未确认前保持主动模式不可用。源车的 `phase_lead_s=0.0135`、杆臂、轮向微调、噪声和控制增益均不直接移植；相位提前先设为 0，且仅在独立辨识和验证后再讨论开启。

## 6. 分阶段实施和检查

### 阶段 0：确认输入与测量基线

- [ ] 记录实际编译配置、固件身份、Flash 参数、现有 PID 和功控，核对四轮轮位、旋向、轮径/轴距/轮距和减速比，区分源码默认值与实际生效值。
- [ ] 明确 MPU6500 实际固定位置、是否随 yaw/pitch 转动、安装轴、云台零位、IMU 和云台中心到车体中心的三维杆臂；确认各传感器的数据路径和失效行为。
- [ ] 测量轮反馈、INS 的真实接收时序、抖动、延迟与互相偏差；采集静止、平移、自旋和组合工况。样本时间未知就保留未知，不能据此宣称融合精度达标。

### 阶段 1：移植与主机验证（默认关闭）

- [ ] 引入源 KF/运动学的必要代码及原许可，解决同名头文件、include guard、全局符号和滤波库冲突；核实目标构建系统 `Makefile` 与 `CMakeLists.txt` 均包含正确文件。
- [ ] 适配 INS 的一致性快照、轮反馈、时钟及坐标；采用真实序号，缺失或超时输出明确无效位。补齐需要的姿态/杆臂恢复能力；缺条件时不启用对应观测。
- [ ] 将参考 `tests/chassis_fusion_test.c`、`chassis_observation_guard_test.c`、`chassis_control_permission_test.c`、`chassis_motion_rigid3d_test.c` 等相关测试移植并适配；增加目标车坐标、轮向、单位、时间回绕/乱序/重复、样本偏斜、重力去除和杆臂、掉线恢复及非有限数故障注入。
- [ ] 增加控制链对照测试：相同输入下关闭与影子模式的四轮实际目标、功率预算、安全使能和 CAN 输出相同；独立力控构建不受影响。验证估计不改变既有 `ChassisGetVelocitySnapshot()` 及已发布协议。
- [ ] 执行已有 `tests/chassis_velocity`、`tests/chassis_motion`、`tests/chassis_kinematics` 与相关功控测试，参考各目录 Makefile 的实际 target；运行目标工程验证脚本和以下三套构建，并检查 Flash/RAM、栈、堆、最大执行时间与任务周期：

### 阶段 2：影子实测和参数辨识

- [ ] 由具备硬件条件的人员先完成静止和架空，再以低速地面直行、横移、停车、换向、自旋和组合动作采集。记录同步的轮速、IMU、已有轮速里程计、KF 和候选输出，以及功控/限流状态。
- [ ] 划分互不重叠的辨识与验证数据，先冻结噪声、时间对齐和评估门槛，再以独立数据评价。条件允许时引入独立速度/位姿测量；仅与轮速里程计一致不能证明真实速度准确，打滑时尤其如此。
- [ ] 在各工况检查创新、拒绝原因和有效率；单独验证 IMU 故障、轮反馈丢失、时钟异常与恢复、急停和模式切换。记录最坏任务耗时、最小栈/堆余量及数据丢失；超预算或不能解释异常则保持影子。
- [ ] 结合测量噪声、仪器精度和安全边界，事先确定允许误差、响应退化上限、资源预算和通过所需的重复试次；目前没有数据支撑，不能给出可信数值或宣称通过。

### 阶段 3：主动补偿另行评审

- [ ] 阶段 2 有独立测量证据后，冻结小增益、最大补偿、变化率及恢复参数；先在架空/受限条件验证，然后低速对照原控制并逐步扩大工况。
- [ ] 验证每种保护触发时补偿立即撤销、原有急停和功率约束始终生效，确认抖动、过冲、停车距离及资源占用没有超过事先冻结的界限；达不到时关闭补偿并保留原控制。
- [ ] 形成软件测试与硬件验收分开的记录；没有实车证据时，结论只能是软件/影子阶段完成，不能标为主动控制验收通过。
